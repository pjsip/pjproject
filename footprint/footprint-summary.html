Does PJSIP fit in 640 KB?

For SIP Spectrum's exact target — 4 concurrent bidirectional TLS+SRTP calls with G.711 and G.722 mixed, plus one receive-only stream, on an STM32H563 (Cortex-M33, 2 MB flash, 640 KB RAM). We measured a real build instead of guessing. Flash fits at ~52 %. RAM does not fit 640 KB — not even after tuning. Static plus heap totals ~704 KB tuned and ~0.9–1.1 MB at the call-setup peak. This corrects an earlier, more optimistic read that had modeled a lighter single-codec scenario.

Static and heap are separate, additive SRAM regions, plus ~40 KB of thread stacks and lwIP pools on top. To fit 640 KB you would drop below pjsua-lib to raw pjsip+pjmedia (removing the 88 KB preallocated call array and the conference-bridge/resampler ports), cut the jitter buffer hard, or pick a part with ~1 MB SRAM.

1Peak heap high-water mark — not a pool-fill percentage

The old public page reported pool utilization against a preallocated size. That is not the number that decides a part. Here is the peak malloc high-water mark and the settled steady level for the exact scenario, captured two independent ways that agree to within 0.2 %: valgrind massif, and an LD_PRELOAD allocator shim that records live and peak malloc'd bytes the same way an instrumented allocator does. Both count every library's heap — pjlib pools, mbedTLS, libsrtp, glibc.

The ARM32 and x86-32 figures are identical to within 0.2 % — both are 32-bit, and the heap is dominated by buffers of the same size on either ISA. This is the modern-ARM figure requested; a Cortex-M part itself was not run, because there is no in-tree RTOS or bare-metal port. "Embedded-tuned" is PJSUA_MAX_BUDDIES 8 + mbedTLS 4 KB record buffers + 200 ms jitter buffer; it moves the heap only ~20 KB, because the buddy table is static RAM and the heap is dominated by the preallocated call array and per-call pools those knobs don't touch.

The peak is a call-setup transient: all five streams came up within ~20 s, so their SIP transaction buffers stacked, then aged out ~32 s later, leaving steady ~210–240 KB lower. Staggered arrival lowers the peak; four simultaneous incoming INVITEs sit near it.

Static (.data+.bss) and heap (malloc) are separate memory: the 88 KB call array is on the heap, the 158 KB buddy table is static, no overlap. Even the tuned steady total is ~49 KB over 640 KB, and sizing for the setup peak needs ~0.9–1.1 MB — before ~40 KB of thread stacks and lwIP. Flash, by contrast, is comfortable: ~1.03 MiB of 2 MB.

This corrects the earlier read. A first pass modeled 4 single-codec G.722 calls (heap 561 KB) and found that buddies=8 fit with ~22 KB spare. The prospect's 4+1 mixed scenario carries ~92 KB more heap — the fifth stream plus resampler state for the 8 kHz G.711 ports on the 16 kHz bridge — so the same tuned config lands at 704 KB and no longer fits. The heavier scenario is the one that governs the part choice.

3Calibrating against libre's ~25 KB

A ~25 KB steady libre figure and this ~653 KB PJSIP figure differ ~26×. The gap is real and mostly architectural, but part of it is the denominator, and it is worth being explicit so the comparison is fair.

  • What the PJSIP bytes buy (peak attribution): pjlib pools 813 KB — the 88 KB preallocated call array, ~16 KB/stream jitter buffers at the 500 ms default, and INVITE/dialog/transaction pools; mbedTLS record buffers 33.5 KB; libsrtp ~16 KB; glibc stdio 12 KB.
  • Likely not apples-to-apples. An allocator that instruments only libre's own mem_alloc/mem_deref will not see OpenSSL/mbedTLS record buffers, libsrtp contexts, or static arrays at all. If the 25 KB is libre-core-only, the honest comparison to our all-in 653 KB is our pjlib-pools-only figure of ~460–530 KB — still ~20×, but not 26×.
  • The gap is design, not measurement error. PJSIP via pjsua-lib is a batteries-included high-level stack that preallocates and pools; libre is a lean core. If 640 KB is a hard constraint, that difference is exactly what decides the part.

4G.711-vs-G.722 CPU — the DSP-vs-MCU question

Measured on PJSIP's own codecs (codec_bench.c): encode + decode of one 10 ms frame, counted by callgrind instruction reads and native wall-clock.

Codecinstructions / frameµs / frame (x86-32)
G.722 @ 16 kHz219,48128.2
G.711 computed (minimal-size default)9,6131.02
G.711 table-based2,0960.35

The ratio is 23× with computed G.711 and 105× with table-based G.711. The old "~55× on ARM9" figure sits between, consistent with a table build. The reason it swings so much: G.722 is the fixed cost — plain-C fixed-point, a 24-tap QMF filter and full sub-band ADPCM at twice G.711's sample rate, no DSP intrinsics — so the ratio is governed entirely by whether G.711 is a lookup or computed. The minimal-size preset compiles the tables out, which is why the default ratio is ~23×.

For the decision: four G.722 calls run ~88 M instructions/s of codec work — roughly a third to half of a 200–250 MHz Cortex-M core, before RTP, SRTP, jitter and mixing. Four G.711 calls run ~3.8 M/s: negligible. That is the gap that justifies a DSP or hardware codec path — G.722 in software is a real MCU load; G.711 is not. Two adjacent notes: a mixed device also pays software resampling and packet-loss concealment, and the H563's on-chip AES/HASH could offload the SRTP crypto, which libsrtp is not wired to by default.

5Caveats — for the record

Measured on pjproject 2.17 + mbedTLS 3.6.7 in the exact feature set described (G.711/G.722 + telephone-event, SDES-SRTP, SIP over TLS via mbedTLS, no video, no ICE/STUN/TURN). Heap high-water marks are from 32-bit x86 and a 32-bit ARM build under user-mode emulation, both under a heap profiler with real TLS+SRTP calls up; a bare-metal malloc differs slightly in per-allocation overhead. Flash and static RAM come from an ARM Thumb-2 cross build at -Os with dead-code elimination — a close proxy for Cortex-M33 code size, but linked against Linux glibc, so C-library, RTOS and IP-stack footprint are not included. There is no in-tree Zephyr or FreeRTOS port, so PJLIB's OS abstraction would need porting on the customer side, and neither its footprint nor lwIP's is in these numbers. The receive-only fifth stream is a SIP-signalled held call, an upper bound; a raw RTP listener would cost less.
